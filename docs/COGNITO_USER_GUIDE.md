# Cognitoユーザー向けログイン・アカウント統合手順書

## 1. この手順書の前提

RAiMでは、標準Cognitoユーザーを正規アカウントとし、Googleを同じユーザーへリンクする。

```text
Cognitoユーザー 1件
 ├─ メールアドレス・パスワード
 └─ Google連携（identities）
```

同じメールアドレスであるだけでは、Cognitoはユーザーを自動統合しない。Googleの検証済み属性と固有IDをAWS側で確認し、`AdminLinkProviderForUser`によるリンク処理を行う。

この手順書のGoogle先行フローは、次の機能がAWS側に導入済みの場合だけ使用する。

- Inbound federation Lambda
- Account Link API
- 標準ユーザー作成・リンク処理
- 既存ユーザー移行手順

Account Link APIが未導入の環境では、ユーザー自身でアカウントを統合しようとせず、管理者へ連絡する。

ユーザーがAWSアクセスキー、IAM権限、Cognitoの`sub`、Cognitoの`Username`を入力することはない。

## 2. 標準ユーザーを先に作成した場合

### 2.1 初回登録

1. メールアドレスとパスワードで標準ユーザーを作成する
2. Cognitoから届くメールの認証を完了する
3. メールアドレスとパスワードでログインする

### 2.2 後からGoogleをリンクする

1. ログイン画面で「Googleでログイン」を選択する
2. 標準ユーザーと同じ、検証済みメールアドレスのGoogleアカウントを選択する
3. Google認証を完了する
4. 標準ユーザーとしてログインできることを確認する

AWS側では次の条件をすべて満たす場合だけ、自動リンクする。

- Googleの`email_verified`が`true`
- 標準ユーザーのメールアドレスが検証済み
- 一致する標準ユーザーが1件だけ
- 同じGoogleの`sub`が別ユーザーへリンクされていない

同じGoogleユーザーの新規Cognitoプロファイルが作成された場合、リンクに失敗している。別アカウントを作成せず、管理者へ連絡する。

## 3. Googleユーザーを先に作成した場合

### 3.1 Account Link API導入後

1. 「Googleでログイン」を選択する
2. Google認証を完了する
3. アカウント設定で「アカウントを統合してパスワードを設定」を選択する
4. パスワードポリシーを満たす新しいパスワードを入力する
5. Account Link APIで保存する
6. 成功メッセージを確認する
7. 案内に従ってログアウトし、再ログインする
8. Googleログインとメールアドレス・パスワードログインを確認する

この処理では、標準ユーザーを正規アカウントとして作成し、Googleの`sub`を標準ユーザーへリンクする。パスワードは標準ユーザー側に設定される。

統合処理の途中で失敗した場合は、再登録やユーザー削除を行わず、表示された受付番号または時刻を添えて管理者へ連絡する。

### 3.2 Account Link API未導入の環境

`/account/password` APIは、ログイン後のメニューからパスワードを変更するためのAPIである。現在のパスワードを必須とし、Cognitoの`ChangePassword`を実行する。Googleユーザーへ管理者権限でパスワードを設定するAPIではない。

Googleのみのユーザーは、現在のパスワードを持たないため、このAPIを初回パスワード設定には使用できない。Account Link APIで標準ユーザーへ統合する。

そのため、次の場合は旧APIをアカウント統合の目的で使用しない。

- 標準ユーザーを作成したい場合
- Googleユーザーと標準ユーザーを1件にまとめたい場合
- 既存ユーザーのアプリデータを移行したい場合

この場合は管理者による移行が必要になる。

## 4. 既にGoogleユーザーだけが存在する場合

ユーザー自身で同じメールアドレスの標準ユーザーを作成し直さない。Cognitoの`sub`が変わり、アプリデータが分離する可能性がある。

管理者へ次の情報を伝える。

- 使用しているGoogleアカウントのメールアドレス
- Googleログインができること
- アプリ内のユーザーデータを保持する必要があるか
- 発生した日時と画面のエラーメッセージ

管理者は、Googleの`sub`、Cognitoの`sub`、アプリデータをバックアップしたうえで標準ユーザーへ移行する。ユーザーの同意とバックアップなしに、Googleユーザーを削除しない。

## 5. 標準ユーザーとGoogleユーザーの両方が存在する場合

ユーザー自身でどちらかを削除しない。原則として標準ユーザーを正規アカウントとして残し、管理者が次の処理を行う。

1. 両方のユーザーを特定する
2. 本人確認を行う
3. 両方のアプリデータを比較・バックアップする
4. 標準ユーザーの`sub`へデータを移行する
5. Googleの`sub`を標準ユーザーへリンクする
6. リンク成功を確認する
7. 必要な場合だけ重複Googleプロファイルを整理する
8. Googleとパスワードの両方でログインを確認する

メールアドレスが同じという理由だけで、自動削除・自動統合は行わない。

## 6. アカウント設定画面の表示ルール

アカウント状態はAWS側で判定し、クライアントはその結果を表示する。

| 状態 | 表示する操作 |
|---|---|
| Googleのみ・未統合 | アカウントを統合してパスワードを設定 |
| 標準ユーザー・パスワード設定済み | パスワードを変更 |
| Googleと標準ユーザーが重複 | アカウント統合を中断し、管理者へ連絡 |
| 状態を取得できない | パスワード操作を表示せず、再ログインを案内 |

クライアントはメールアドレスだけで状態を推測しない。画面にパスワード設定ボタンが表示されていても、未認証状態でAPIを呼び出してはいけない。

## 7. パスワード変更

統合済みのユーザーは、アカウント設定から「パスワードを変更」を選択する。

1. 現在のパスワードを入力する
2. 新しいパスワードを2回入力する
3. 保存する

アプリはパスワード変更APIへ現在のパスワードと新しいパスワードをHTTPSで送信し、バックエンドLambdaがCognitoの`ChangePassword`を実行する。アプリクライアントとOAuth要求には次のスコープが必要である。

```text
aws.cognito.signin.user.admin
```

LambdaはBearerアクセストークンから対象ユーザーを特定し、リクエストボディから`Username`や`sub`を受け取らない。既存アクセストークンにはスコープ変更が反映されないため、スコープ変更後はログアウトして再ログインする。

## 8. パスワード再設定

パスワードを忘れた場合は、アプリ内APIではなくCognito Managed Loginの「パスワードを忘れた場合」を使用する。

再設定には次が必要である。

- 標準ユーザーであること
- `email`が正しいこと
- `email_verified`が`true`であること
- User Poolのアカウント復旧で`verified_email`が有効であること

メールが届かない場合は、迷惑メール、受信拒否、メール送信設定を確認する。Googleだけの既存プロファイルを標準ユーザーへ移行する前に、パスワード再設定を繰り返さない。

## 9. パスワードポリシー

現在のCognito User Poolでは、次の条件を満たす必要がある。

- 8文字以上
- 英大文字を1文字以上
- 英小文字を1文字以上
- 数字を1文字以上
- 記号を1文字以上

この表示はCognito側の設定と一致させる必要がある。Cognito側のポリシーを変更した場合は、クライアントの表示も同時に更新する。最終的な判定はCognitoが行う。

## 10. エラー時の対応

### 「ユーザー名またはパスワードが正しくありません」

- GoogleボタンではなくCognitoのメールアドレス・パスワード入力を使用したか確認する
- アカウント統合が完了しているか確認する
- 同じメールアドレスの重複ユーザーがないか管理者に確認する
- 解決しない場合はパスワードを何度も試さず、管理者へ連絡する

### 「アカウント統合に失敗しました」

ユーザーを削除・再作成せず、表示された時刻とエラーを管理者へ連絡する。リンク処理は管理者が再実行可能な手順で行う。

### 「認証に失敗しました。再ログインしてください」

一度ログアウトし、Cognito Managed Loginから再ログインする。アクセストークンの期限切れや、統合前の古いセッションが原因になることがある。

## 11. セキュリティ上の注意

- メールアドレス一致だけでアカウントをリンクしない
- Googleと標準ユーザーのメール検証状態を確認する
- Googleの恒久識別子はメールアドレスではなく`sub`を使用する
- AWS管理APIをクライアントから呼び出さない
- AWSアクセスキーやIAM権限をアプリへ含めない
- パスワードをログやアプリデータへ保存しない
- 統合前にアプリデータをバックアップする
- 統合処理後は一度ログアウトして、新しい標準ユーザーで再ログインする
- サポート担当者へパスワードや認証コードを伝えない
