# Flutter プロジェクト構造の解説（班員向け）

## このドキュメントについて

RAiMプロジェクトでFlutter（フロントエンド）の開発に関わる班員向けの解説資料。
プロジェクトのコードを「**なぜこの構造にしているのか**」「**どこに何を書けばいいのか**」を理解するためのもの。

Flutter初心者でも読めるように書いてあるので、まずはこれを読んでから実装に入ること。

---

## 大前提：なぜ「構造」が必要なのか

「1つのファイル `main.dart` に全部書いちゃダメ？」

技術的にはダメじゃない。動くものは作れる。でも、

- 1000行を超えると読めなくなる
- 「LLM呼び出し処理どこ？」を探すのに時間かかる
- バグ修正のとき影響範囲がわからない
- 班員と分業できない（同じファイル触ると衝突）
- 後から「Ollama → Bedrock」みたいな変更が地獄

これを解決するのが「**役割ごとにファイルを分ける**」という考え方。
プログラミングの普遍的な設計原則。

---

## Flutterの基本ディレクトリ

Flutterプロジェクトを作ると、こんなディレクトリができる：

```
raim_app/
├── lib/              ← 自分が書くコードはここ
│   └── main.dart     ← アプリの起点
├── android/          ← Android固有の設定（基本触らない）
├── ios/              ← iOS固有の設定（基本触らない）
├── windows/          ← Windows固有の設定（基本触らない）
├── web/              ← Web固有の設定（基本触らない）
├── pubspec.yaml      ← パッケージ管理（package.jsonと同じ役割）
└── test/             ← テストコード
```

書くコードは全部 `lib/` の中。`main.dart` がエントリーポイント（アプリ起動時に最初に動く）。

**React/TypeScriptとの対応**:
- `lib/` ≒ `src/`
- `main.dart` ≒ `index.tsx`
- `pubspec.yaml` ≒ `package.json`

---

## RAiM の `lib/` フォルダ構成

```
lib/
├── main.dart
├── models/              ← データの形を定義
├── services/            ← 外との通信処理
├── providers/           ← アプリ全体の状態管理
├── screens/             ← 画面そのもの
└── widgets/             ← 画面の部品
```

この5つに分ける理由は、**それぞれが「違う種類の責任」を持つから**。
順番に説明する。

---

## 各フォルダの役割

### `models/` — データの形を定義する場所

「データの設計図」を置く場所。

例：「メッセージ」って何？と聞かれたら、

- 誰が言ったか（user / assistant）
- 何を言ったか（text）
- いつ言ったか（timestamp）
- どんな感情か（emotion）

これがデータの構造。コードで書くとこうなる：

```dart
class Message {
  final String text;
  final String role;  // "user" or "assistant"
  final DateTime timestamp;
  final String? emotion;
  
  Message({
    required this.text,
    required this.role,
    required this.timestamp,
    this.emotion,
  });
}
```

これを `lib/models/message.dart` に置く。**データの形だけを定義するファイル**。

TypeScript で言うと `interface Message { ... }` や `type Message = { ... }` に近い。
Dartは型に厳しいので `class` で書く。

**なぜ分けるか**:
- データ構造を変えたいとき、ここだけ修正すれば済む
- 他のファイルから `import 'package:raim_app/models/message.dart';` で使える
- データ構造が一目でわかる

---

### `services/` — 外と通信する処理を書く場所

「外部とやり取りする処理」を置く場所。

外部とは：
- Ollama（HTTP通信）
- Bedrock（HTTPS通信）
- Unity（WebSocket通信）
- ファイル保存（ローカルストレージ）

これらをUIと混ぜると地獄になる。なぜなら：

- UIファイルが肥大化する
- LLM呼び出しの単体テストができない
- Ollama → Bedrock 切り替えのとき、UIまで修正することになる

なので「**外との通信ロジックだけ**」を独立させる。

例：`lib/services/llm_service.dart` には「LLMに問い合わせる処理」だけが入る：

```dart
class OllamaService {
  Future<LLMResponse> sendMessage(String userInput) async {
    // ここで http.post('http://localhost:11434/api/chat', ...) を実行
    // レスポンスを LLMResponse に変換して返す
  }
}
```

UI側は「OllamaServiceを呼ぶ」とだけ書けばよくなる。
**UIは通信の詳細を知らなくていい**。

---

### `providers/` — アプリ全体の状態を管理する場所

「アプリ全体で共有するデータ」を管理する場所。

例：チャット履歴。これは

- チャット画面で表示する
- 設定画面で「履歴を消す」ボタンがあるかも
- Unity連携でも参照したい

複数の画面・コンポーネントから触る。これを「**グローバルな状態**」と呼ぶ。

ReactでContextやReduxを使ってグローバル状態管理するのと同じ。
Flutterではこれを `Provider` や `Riverpod` というライブラリでやる。

`lib/providers/chat_provider.dart` には：

```dart
class ChatProvider extends ChangeNotifier {
  List<Message> messages = [];  // チャット履歴
  bool isLoading = false;        // LLM応答待ち中か
  
  Future<void> sendUserMessage(String text) async {
    // ユーザーメッセージを履歴に追加
    messages.add(Message(text: text, role: "user", ...));
    notifyListeners();  // UI更新を通知
    
    // OllamaServiceを呼んでLLM応答を取得
    isLoading = true;
    notifyListeners();
    
    final response = await ollamaService.sendMessage(text);
    
    // 応答を履歴に追加
    messages.add(Message(text: response.text, role: "assistant", ...));
    isLoading = false;
    notifyListeners();
  }
}
```

ここに「**ユーザー入力からLLM応答までの一連の流れ**」が集約される。
UIはここを呼ぶだけ。

React + Reduxで言うと、ReducerやActionに相当する場所。

---

### `screens/` — 画面そのもの

「ユーザーが見る画面」を置く場所。

例：チャット画面、設定画面、ログイン画面など。

`lib/screens/chat_screen.dart` には：

```dart
class ChatScreen extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text('RAiM')),
      body: Column(
        children: [
          Expanded(child: MessageList()),  // メッセージ一覧
          ChatInput(),                       // 入力欄
        ],
      ),
    );
  }
}
```

画面の**レイアウト**を書く場所。

React で言うと `src/pages/` や `src/screens/` に対応。

---

### `widgets/` — 画面の部品

「画面の中で使う、小さい部品」を置く場所。

例：

- メッセージの吹き出し（MessageBubble）
- 入力欄（ChatInput）
- キャラクター表示エリア（CharacterDisplay）

これら全部 `screens/chat_screen.dart` に書いてもいいけど、

- chat_screen.dart が肥大化する
- 同じ部品を別の画面でも使いたい時に再利用できない
- テストしにくい

なので部品ごとに分ける。

`lib/widgets/message_bubble.dart`:

```dart
class MessageBubble extends StatelessWidget {
  final Message message;
  
  const MessageBubble({required this.message});
  
  @override
  Widget build(BuildContext context) {
    return Container(
      padding: EdgeInsets.all(8),
      // メッセージの吹き出しの見た目
    );
  }
}
```

React で言うと `src/components/` に置くコンポーネントと同じ。

## 全体の流れ：データの旅

ユーザーが「おはよう」と入力したときの旅を追ってみる：

```
[ChatInput (widgets/)]  ← ユーザーが入力
   ↓ 「送信」ボタン押す
[ChatScreen (screens/)]  ← 入力を受け取る
   ↓
[ChatProvider (providers/)]  ← 「LLMに送信して」と指示
   ↓
[OllamaService (services/)]  ← Ollamaに HTTP POST
   ↓
[Ollama (外部プロセス)]  ← 推論
   ↓
[OllamaService (services/)]  ← レスポンス受信、Message型に変換
   ↓ 戻る
[ChatProvider (providers/)]  ← メッセージ履歴に追加、notifyListeners()
   ↓
[ChatScreen (screens/)]  ← 自動で再描画
   ↓
[MessageBubble (widgets/)]  ← 新しいメッセージが画面に表示
```

これが「**役割分担**」ってこと。各ファイルは自分の仕事だけやる。

## この設計のメリット（具体例）

### 例1：Ollama → Bedrock に切り替える

- 変更するファイル：`services/llm_service.dart` だけ
- 他のファイルは無傷
- UIもプロバイダーも変更ナシ

### 例2：メッセージにアイコンを追加したい

- 変更するファイル：`widgets/message_bubble.dart` だけ
- ロジック側は無傷

### 例3：チャット履歴を保存する機能を追加

- 新規ファイル：`services/storage_service.dart`
- 変更ファイル：`providers/chat_provider.dart` だけ
- UIは無傷

### 例4：班員が並列で作業する

- A：UIの見た目を作る → `widgets/`, `screens/`
- B：LLM接続を作る → `services/`
- C：状態管理を整える → `providers/`
- 衝突しない

## TypeScript/Reactとの対応表

| Flutter | React/TypeScript |
|---|---|
| `lib/main.dart` | `src/index.tsx` |
| `lib/models/` | `src/types/` |
| `lib/services/` | `src/api/`, `src/services/` |
| `lib/providers/` | `src/store/`, `src/contexts/` |
| `lib/screens/` | `src/pages/` |
| `lib/widgets/` | `src/components/` |
| `pubspec.yaml` | `package.json` |

**同じ考え方を、別の言語・フレームワークでやっているだけ。**
NewsTrendRating等で書いてきたReactの構造の知識がそのまま使える。

## どこを編集すればいいか早見表

「○○したい」と思ったとき、どこを編集すればいいか：

| やりたいこと | 編集する場所 |
|---|---|
| LLMの送信先を変える（Ollama→Bedrock） | `services/llm_service.dart` |
| システムプロンプトを変える | `services/llm_service.dart` |
| メッセージの見た目を変える | `widgets/message_bubble.dart` |
| 画面のレイアウトを変える | `screens/chat_screen.dart` |
| 新しい状態を追加する（例：ユーザー設定） | `providers/` に新規ファイル |
| 新しいデータ型を追加する | `models/` に新規ファイル |
| Unity との通信処理 | `services/unity_bridge.dart` |
| ボタンの動作を変える | `widgets/` の該当ファイル |

## まとめ

5つに分ける理由：

1. **役割を明確にする** → 「ここは何の処理？」が一目でわかる
2. **変更の影響範囲を狭める** → 1箇所の修正で済む
3. **再利用しやすくする** → 同じ部品を別画面でも使える
4. **班員と並列作業できる** → 衝突しない
5. **テストしやすい** → 各部分を独立してテストできる
6. **本番移行が楽** → サービス層だけ差し替え

これは**Flutterに限らない、ソフトウェア設計の普遍原則**。
一度身につければ他の言語・フレームワークでも使える。
