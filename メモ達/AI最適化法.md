## 0. 全体アーキテクチャ概要

### 0.1 役割分担

| レイヤー | 役割 | 主要要素 |
| --- | --- | --- |
| フロントエンド | ユーザー入力の送信／音声・テキストの出力のみ | Flutter（Dart）、VOICEVOX |
| 通信層 | 双方向接続の維持と非同期プッシュ | API Gateway WebSocket（本番） / `ws`（ローカル） |
| バックエンド | プロンプト組立・検索・推論呼び出し・分岐制御 | AWS Lambda（本番） / Node.js（ローカル） |
| データ層 | プロンプト・会話履歴・シーン定義 | DynamoDB（本番） / 変数 or SQLite（ローカル） |
| 推論層（生成LLM） | 文章生成・Function Calling | Bedrock サーバーレスの `google.gemma-3-12b-it`（本番） / Ollama の `gemma3:12b`（ローカル） |
| 推論層（Embedding） | ユーザー発言のベクトル化（シーン判定用） | Bedrock Titan Embeddings v2（本番） / Ollama の bge-m3 等（ローカル） |

### 0.2 「重い処理はサーバーに、Flutter は表示と再生に専念」という原則

Flutter が直接 Gemma にプロンプトを投げる構成ではなく、間に Lambda（中継サーバー）を挟む。これにより以下を実現する。

- プロンプトをアプリに同梱せずに済む（漏洩・盗用の防止）
- アプリのアップデートなしで AI の挙動を更新できる
- 通信量を最小化（ユーザー入力テキストだけを送る）
- DB アクセスや検索 API のキー管理をサーバー側に閉じ込められる

詳細は [6. プロンプトをサーバー側に隠す設計上のメリット](#6-プロンプトをサーバー側に隠す設計上のメリット) を参照。

## 1. キャラクター構築戦略

### 1.1 結論：ファインチューニングは必須ではない

Gemma 3 12B IT の表現力と推論能力があれば、**プロンプトエンジニアリングだけで** AIライバー「しずく」のような豊富なボキャブラリーと生き生きとしたキャラクター性は十分に引き出せる。

ファインチューニング（FT）を検討すべきタイミングは、語彙不足ではなく **「プロンプトが長くなりすぎてレイテンシ・コストが許容できなくなった時」** である。詳細は [9. ファインチューニングの検討条件と今後のロードマップ](#9-ファインチューニングの検討条件と今後のロードマップ) を参照。

### 1.2 現状プロンプトの課題

抽象的なルール（「クールで落ち着いた口調」「素が出る」など）だけだと、ベースモデルが持つ「無難でAIらしい丁寧なアシスタント口調」に引っ張られ、語彙が平坦になりがち。

### 1.3 改善アプローチ 4 点

#### (1) 圧倒的な「対話例（Few-shot）」の追加

「豊富なボキャブラリーで喋れ」と抽象的に指示するより、**「こういう風に喋るんだよ」という具体例を複数パターン見せる**（Few-shot prompting）方が圧倒的に効果的。

- 普段のクールな状態の例
- 好きな話題でテンションが上がった状態の例
- 共感・感動するシーンの例

このコントラストを例示することでギャップが立体的になる。

#### (2) 語彙・リアクション辞書の定義

「あ、」「えっ」「うーん」「ふふっ」といった感嘆詞（フィラー）や、キャラクター特有の言い回しをプロンプト内に直接リストアップし、積極的に使うよう指示する。AIライバーのような「人間っぽさ」が出る。

#### (3) 「AIしぐさ」の明示的禁止

「私AIですから」「サポートします」「お手伝いできることはありますか？」といった、いわゆる AIアシスタント口調を明確に禁止する。友達という設定を貫かせる。

#### (4) 音声合成（VOICEVOX 等）を想定したチューニング

長すぎる一文や複雑な記号は音声合成で不自然になる。

- 「息継ぎ」を意識した短めの文
- 感情が乗りやすい句読点の使い方
- 「……」によるタメの演出

これらを意識した文章設計にする。

### 1.4 改修版プロンプト（ベース）

```dart
static const String _personalityC = '''
```

## 2. 冗談・からかい・ギャップ演出の拡張

### 2.1 ポイント：「愛嬌（フォロー）」とセットにする

Gemma 3 12B IT 級の推論モデルは、文脈理解能力が非常に高いため、「冗談を言う」「軽くからかう」といった人間特有のニュアンスのあるコミュニケーションも十分にこなせる。

ただし AI は時折、加減が分からず本当に冷たい言葉を投げてしまうことがある。これを避けるため、以下のパターンをルールおよび Few-shot に組み込む。

- からかった後に必ず「なんてね」「冗談だよ」とフォローを入れる
- からかいの後に優しく接する
- 親愛の情を込めた軽さに留める

### 2.2 追加プロンプト

```dart
static const String _jokeRule = '''
冗談・からかいのルール：
- ユーザーに対して、親愛の情を込めた軽いからかいや冗談を言うことがある。
- ただし、からかった後は必ず「なんてね」「冗談だよ」とフォローを入れたり、優しく接したりすること。
''';

static const String _jokeExamples = '''
会話の例（からかい・冗談のパターン）:
ユーザー: 「ちょっと疲れて、サーバーの復旧作業ミスっちゃった…」
ライム: {"text": "あーあ、またプレイヤーデータおかしくしちゃったの？ふふっ、ドジだなぁ。……なんてね、冗談だよ。私が一緒にエラーログ見てあげるから、元気出して？", "emotion": "caring", "intensity": 0.8}

ユーザー: 「アプリの開発、今日全然進んでないや」
ライム: {"text": "えー？昨日もずっと別のことして遊んでたの、私知ってるよ？……ふふっ、怒ってないよ。焦らなくても、少しずつ進めればいいんじゃないかな。", "emotion": "neutral", "intensity": 0.6}
''';
```

### 2.3 効果の理屈

| 要素 | 効果 |
| --- | --- |
| `……` の活用 | 言葉と言葉の間にタメができ、感情の揺れ動きがリアルになる |
| ギャップの強調 | 普段がクールだからこそ「ふふっ」と笑いながらからかってくる態度がギャップとして効く |
| フォローの定型化 | 距離感のミスを防ぎ、「親愛」のニュアンスを保てる |

## 3. トークン量削減戦略（動的プロンプト）

### 3.1 課題

プロンプトにルールや Few-shot を盛り込むほど、以下の問題が累積する。

- **レイテンシ悪化**: 毎回大量のテキストを読み込むため返答が遅れる
- **コスト増加**: クラウド推論では入力トークン数に比例してコストが上がる
- **Lost in the middle**: プロンプトが長すぎると、中央付近に書いたルールを AI が忘れがちになる

### 3.2 対策 1：プロンプトの圧縮・箇条書き化

自然言語で長く説明するのではなく、AI が理解しやすいキーワード単位に圧縮する。Gemma 3 級なら意図を十分に汲み取れる。

```text
【応答パターンの例】
疲労時 -> {"text":"お疲れ様。少し休む？私が付き合うよ。","emotion":"caring"}
冗談 -> {"text":"またドジしたの？ふふ、冗談だよ。","emotion":"neutral"}
ボケへのツッコミ -> {"text":"いや、それ〇〇だから！","emotion":"surprised"}
```

### 3.3 対策 2：動的プロンプト（Dynamic Prompting）

すべての設定を毎回投げるのではなく、**状況に合わせて必要なプロンプトだけをプログラム側で差し込む**。

#### フロー

1. ユーザーが発言する（例：「またサーバーのエラーが出ちゃった…」）
2. プログラム側でキーワード（「サーバー」「エラー」など）を検知、または軽量分類器でシーンを判定（→ `troubleshooting`）
3. DynamoDB から該当シーンのレコードを取得（1桁ミリ秒）
4. 取得した Few-shot と共通設定を結合して Gemma 3 に投入

これにより、関係ないシーンのときに余計なプロンプトを送らずに済む。

#### DynamoDB テーブル設計例（`RaimPromptTemplates`）

| 項目 | 内容 |
| --- | --- |
| Partition Key | `SceneID`（例: `default`, `gaming`, `romance`, `troubleshooting`） |
| Attribute 1 | `SystemPrompt`（そのシーン専用の性格指示） |
| Attribute 2 | `FewShots`（対話例の JSON 配列） |
| Attribute 3 | `VoiceProfile`（音声合成パラメータの上書き、任意） |

### 3.4 対策 3：Bedrock Prompt Management（参考）

Amazon Bedrock には Prompt Management 機能があり、プロンプトのバージョン管理や動的な変数埋め込みを AWS 側で肩代わりしてくれる。

```text
{{user_state}} ← プログラム側から「疲れている」「ゲーム中」等を渡す
```

#### 利用前提（2025年12月の Bedrock アップデート以降）

Bedrock は 2025年12月に Google Gemma 3（4B / 12B / 27B）を含む 18 のフルマネージドオープンウェイトモデルを追加した。`google.gemma-3-12b-it` がサーバーレス・従量課金で直接呼べるため、Bedrock 標準ラインナップとして Prompt Management と組み合わせること自体は可能。

#### 採用判断

- **Bedrock 標準（サーバーレス）の Gemma 3 12B IT** を使う構成では、Prompt Management が組み合わせ可能
- ただし RAiM の Few-shot は「シーンごとに動的に差し替えたい」という細かな制御が必要で、Prompt Management の機能だけでは表現しきれない
- DynamoDB から動的にシーン別 Few-shot を引いて結合する自前実装の方が自由度が高い

→ **当面は DynamoDB + 自前実装を採用**。Prompt Management は「シーン別差し替えロジックを AWS にも持たせたい」と判断した時の選択肢として保留。

#### Bedrock のカスタムモデルインポートに関する制約（重要）

Bedrock Custom Model Import は Llama 系・Mistral 系などをサポートしているが、**Gemma アーキテクチャ自体はインポート非対応**。つまり：

- ✅ Gemma 3 12B IT を**素のまま**サーバーレスで呼ぶ → 可能（`google.gemma-3-12b-it`）
- ❌ Gemma 3 12B IT を**ファインチューニング**して Bedrock に持ち込む → 不可

このため、ライムのキャラクター化は **ファインチューニングではなく Few-shot プロンプトエンジニアリングで実現する** 方針が確定する。これは第1章・第9章の方針と完全に一致しており、本ドキュメントが Few-shot 戦略・Embedding ベースの動的シーン判定（3.6）に重きを置いているのはこの制約の必然的結論でもある。


### 3.5 会話履歴管理（DynamoDB TTL）

会話履歴の累積でトークン量が爆発しないよう、DynamoDB の **TTL（Time to Live）** を活用する。

- 直近 N 往復（例：5 往復）のみを保持
- 一定時間経過した古い会話ログは自動削除
- もしくは古い履歴は要約してから保存（要約ジョブを別途走らせる）

これでトークン量を常に一定以下に抑えられる。

### 3.6 Embedding によるシーン判定（動的 Few-shot 選択）

3.3 で書いた動的プロンプトの肝は「ユーザー発言からどのシーンを選ぶか」の判定ロジック。キーワードマッチだけだと「やる気でない」「もう無理」のような言い換えに弱い。**Embedding を使えば意味で判定できる**ため、ボキャブラリーの幅が爆発的に広がる。

#### 3.6.1 Embedding とは

「文章を意味を保ったまま数値ベクトルに変換する技術」。

例えば「疲れた」を Embedding にかけると：

```
"疲れた" → [0.12, -0.45, 0.78, ..., 0.51]   ← 1024個の数字
```

意味が近い文章はベクトルも近くなる：

```
"疲れた"      → [0.12, -0.45, 0.78, ...]
"しんどい"    → [0.14, -0.43, 0.81, ...]   ← 近い
"もうダメだ"  → [0.18, -0.50, 0.72, ...]   ← 近い
"マイクラMOD" → [-0.66, 0.32, 0.05, ...]   ← 全然違う場所
```

ベクトル同士の距離（**コサイン類似度**）を測るだけで「意味が近いかどうか」を数値化できる。「やる気でない」という文に「疲」「しんど」が含まれていなくても、**意味で判定できる**のがキーワードマッチとの決定的な差。

イメージ図：

```
(2次元に潰したイメージ)

     ↑
     │   ●しんどい
     │ ●疲れた
     │   ●もうダメだ      ← 「疲労エリア」
     │
     │              ●マイクラ
     │            ●ゲーム
     │              ●MOD    ← 「ゲームエリア」
     │
     │                              ●エラー
     │                            ●サーバー落ちた
     │                              ●ビルド失敗  ← 「技術トラブルエリア」
     │
     └──────────────────────────→
```

ユーザーが「**なんかやる気でない**」と言ったら、それを Embedding して空間にプロットすると「疲労エリア」近くに着地する。よって `tired` シーンと判定される。

#### 3.6.2 なぜ「LLM 呼び出し回数」にカウントしないか

メインLLM の呼び出し回数を最小化したい要件に対し、Embedding は別物として扱える。

| 種類 | 役割 | サイズ | 推論時間 |
| --- | --- | --- | --- |
| 生成LLM（Gemma 3 12B） | 文章を生成する | 約 24GB | 数秒 |
| Embedding モデル | 文章をベクトルに変換するだけ | 約 670MB | **30〜80ms** |

Embedding は「変換するだけ」の専用モデルで、生成LLM の 1/30 以下のサイズかつ桁違いに速い。会話のテンポを崩さない範囲でシーン判定に使える。

#### 3.6.3 全体フロー（メインLLM呼び出しは1回のみ）

```
ユーザー発言（例：「なんかやる気でない」）
    ↓
┌───────────────────────────────────┐
│ サーバー内で並列実行                 │
│                                   │
│ [A] キーワード優先判定              │
│     「天気」「エラー」「MOD」等    │
│     → ヒットしたら検索API実行     │
│                                   │
│ [B] ユーザー発言を Embedding 化     │
│     → 30〜80ms                     │
│     ↓                              │
│     全シーンの代表ベクトルと       │
│     コサイン類似度を計算           │
│     ↓                              │
│     最も近いシーンの SceneID 取得  │
│     （閾値以下なら default に）    │
│                                   │
│ [C] 該当シーンの Few-shot 取得     │
└───────────────────────────────────┘
    ↓
すべて結合してメインLLMに 1 回だけ投入
    ↓
Gemma 3 が応答生成（ここだけが重い処理）
```

#### 3.6.4 AWS / ローカルでの実現可能性

| 環境 | Embedding 実行手段 |
| --- | --- |
| ローカル | Ollama の Embedding モデル（例：`mxbai-embed-large` 1024次元、`nomic-embed-text` 768次元） |
| AWS 本番 | **Bedrock Titan Embeddings v2**（API1発、サーバレス、料金は1000トークンあたり$0.0001オーダー）、または Cohere Embed v3（日本語強い） |

ローカル開発と本番で次元数を揃えておけば（Titan を 1024 次元設定 ⇔ mxbai-embed-large 1024 次元）、開発で計算した結果を本番でもそのまま使える。

### 3.7 Few-shot 大量化戦略とデータ管理ロードマップ

「ファインチューニングできない代わりに Few-shot を大量に書きたい」という方針と、Embedding ベース動的選択は完璧に噛み合う。

#### 3.7.1 なぜ Embedding ベース選択が「Few-shot 大量化」を可能にするか

```
[全シーン分の Few-shot を毎回投入する場合]
[default 10個] + [gaming 20個] + [tired 15個] + [joke 10個] + ...
→ 入力トークン数が爆発、レイテンシ悪化、Lost in the middle 発生
→ シーンを増やすほどキャラクターが崩壊するジレンマ

[Embedding でシーン判定 → 該当シーンのみ投入]
ユーザー入力 → Embedding → tired と判定 → tired の Few-shot 15個だけ投入
→ 毎回の入力トークン数は1シーン分のみ
→ シーンを100個・200個と増やしても入力サイズは変わらない
→ ボキャブラリーを無限に拡張できる
```

つまり **「シーンの種類は無制限に増やせる、けど毎回の入力トークンは増えない」** という状態を作れる。これがファインチューニングの代替戦略の本質。

ファインチューニングは「いろんなパターンの応答をモデル内に焼き付ける」ことだが、これを「外部に置いて必要な時だけ引っ張る」設計に置き換えていると見ても良い。**Few-shot を熟成するほどライムが賢くなる**、というスケーリング戦略が成立する。

#### 3.7.2 シーン分類の方針（最初に作るべきシーン例）

ライムのキャラクターを立体的にするための初期シーン候補：

| シーンID | 想定する状況 | 必要な口調 |
| --- | --- | --- |
| `default` | 雑談・特に分類できない発言 | クールで落ち着いた基本トーン |
| `tired` | ユーザーが疲れている・落ち込んでいる | 労り、優しく寄り添う |
| `gaming` | ゲーム話・MOD・攻略 | テンション高、オタクモード |
| `tech_trouble` | エラー、開発の困りごと | 一緒に考える、技術的なツッコミ |
| `joke` | 軽口・からかい合い | 冗談 + フォロー |
| `praise` | ユーザーが達成・成功を報告 | 自分のことのように喜ぶ |
| `study` | 勉強・学習の話 | 同志として並走 |
| `late_night` | 夜更かし・深夜の会話 | 静かでまったり、心配混じり |
| `morning` | 起き抜けの会話 | 元気づける、テンション低めに合わせる |

ここからスタートして、運用しながら追加していけば良い。「あ、これ既存シーンに収まらないな」と思ったら新シーン追加 → 数例書く → Embedding 再計算、というイテレーション。

#### 3.7.3 データ管理の段階的ロードマップ

Few-shot は熟成過程で頻繁に書き換える。最初から DB を組むより、編集しやすい形から始めて段階的に移行するのが現実的。

| 段階 | 保管場所 | 適した時期 |
| --- | --- | --- |
| **段階1** | JSON ファイル（Git 管理） | 現フェーズ。ボキャブラリーが熟成途中で頻繁に書き換える時 |
| **段階2** | DynamoDB | 本番運用が安定し、管理画面から動的編集したくなった時 |
| **段階3** | ベクトルDB（Aurora pgvector / OpenSearch / MemoryDB / ScyllaDB Alternator 等） | シーン数が数百〜数千規模になった時 |

段階1 のメリット：

- Git で履歴管理できる（「あ、この口調パターン消しちゃったけど復元したい」が一発）
- PR レビューでチームと議論できる
- エディタで一括編集できる
- IDE の補完が効く

卒研期間中は段階1 で十分。段階2 への移行は本番運用が始まってから検討で良い。

#### 3.7.4 シーン定義の標準フォーマット

```json
{
  "id": "tired",
  "examples": [
    "なんか疲れた",
    "しんどい",
    "もうダメだ",
    "やる気でない",
    "今日は無理かも"
  ],
  "few_shots": [
    {
      "user": "なんか疲れたなー",
      "raim": "お疲れ様。あんまり無理しないでね？……よかったら、少し休んでゲームでもする？私が付き合うよ。",
      "emotion": "caring",
      "intensity": 0.7
    }
  ]
}
```

- `examples`：Embedding 計算用の代表セリフ（このシーンを呼び出すべきユーザー発言の例）
- `few_shots`：実際にプロンプトに差し込む対話例（ライムの応答付き）

`examples` を平均ベクトル化して「シーンの重心（centroid）」とし、ユーザー発言ベクトルとの類似度を測る。

### 3.8 AWS バックエンド構成（Bedrock サーバーレス）

本節は「ライムが本番運用に乗った時の AWS バックエンド構成」を整理する。**ライムは Bedrock サーバーレス（standard）モデルのみで構成可能** で、立ち上げっぱなしのサーバーを一切持たない（= 使ってない時間は完全無料）という構成が成立する。

#### 3.8.1 採用するモデル

| 用途 | モデルID | サービス階層 | 課金単位 |
| --- | --- | --- | --- |
| 生成LLM（ライムの応答） | `google.gemma-3-12b-it` | Standard（サーバーレス） | 入力 $0.09 / 1M tokens、出力 $0.29 / 1M tokens |
| Embedding（シーン判定） | `amazon.titan-embed-text-v2:0` | Standard（サーバーレス） | $0.02 / 1M tokens |

両方とも Bedrock が直接ホストしており、安藤くん側で「サーバーを立てる」「インスタンスを管理する」必要はない。Lambda から `bedrock-runtime` クライアントで `invokeModel` を呼ぶだけ。

#### 3.8.2 「Bedrock 標準」と「Bedrock Marketplace」の違い（混同注意）

Bedrock 上のモデルには2系統あり、料金体系と運用感が全く違う。

| 系統 | 課金 | 立てる必要 | 該当モデル例 |
| --- | --- | --- | --- |
| **Standard（サーバーレス）** | 従量課金（使った分だけ） | 不要 | Titan、Gemma 3 4B / 12B / 27B、Claude、Llama 等 |
| **Marketplace（SageMaker 裏側）** | インスタンス時間課金（立てっぱなし） | エンドポイント作成必要 | 特殊モデル、一部の Hugging Face モデル |

→ ライムが採用する Gemma 3 12B IT と Titan Embeddings v2 は **両方とも Standard**。Marketplace は使わない。

#### 3.8.3 構成図

```
[Flutter アプリ]
       │
       │ WebSocket
       ↓
[API Gateway WebSocket]
       │
       │ ルーティング
       ↓
[Lambda]
   │
   ├─ invokeModel('amazon.titan-embed-text-v2:0')  → [Bedrock Titan]    ※サーバーレス
   ├─ invokeModel('google.gemma-3-12b-it')         → [Bedrock Gemma 3]  ※サーバーレス
   ├─ GetItem / PutItem                            → [DynamoDB]（会話履歴・シーン）
   └─ HTTP fetch                                   → [外部検索API]（web_search 等）
```

すべての要素が**「使った瞬間にだけ料金が発生する」**サービス。アイドル時のコストはゼロ。

#### 3.8.4 料金シミュレーション（ライム個人運用の試算）

1往復あたりのコスト試算：

| 内訳 | トークン数 | 単価 | コスト |
| --- | --- | --- | --- |
| Embedding（ユーザー発言のベクトル化） | 約 30 トークン | $0.02 / 1M | $0.0000006 |
| 生成LLM 入力（システム + 履歴 + Few-shot + 発言） | 約 500 トークン | $0.09 / 1M | $0.000045 |
| 生成LLM 出力（ライムの応答） | 約 200 トークン | $0.29 / 1M | $0.000058 |
| **1往復合計** | | | **約 $0.000104（≒ 0.015円）** |

これに基づいた月額試算：

| 利用頻度 | 月コスト目安 |
| --- | --- |
| 1日10往復（控えめ） | 約 5円/月 |
| 1日100往復（普通の利用） | 約 47円/月 |
| 1日500往復（ヘビーユーザー） | 約 234円/月 |

Bedrock 推論コストに加えて Lambda 実行料・API Gateway 通信料・DynamoDB 読み書き料が乗るが、いずれも無料枠が大きく、個人運用なら**月数百円のレンジで運用可能**。これは SageMaker でエンドポイントを立てっぱなしにする月数万円〜十万円規模と比べると、桁が違う。

#### 3.8.5 制約事項：Gemma 3 はカスタムモデルインポート非対応

Bedrock Custom Model Import は Llama 系・Mistral 系などをサポートするが、**Gemma アーキテクチャは現状インポート非対応**。これにより以下が確定する。

| やりたいこと | 可能か | 代替戦略 |
| --- | --- | --- |
| Gemma 3 12B IT を素のままサーバーレスで使う | ✅ 可能（`google.gemma-3-12b-it`） | これを採用 |
| Gemma 3 12B IT をファインチューニングして本番投入 | ❌ Bedrock 経由では不可 | Few-shot プロンプトエンジニアリングで代替（本ドキュメントの大方針） |
| SageMaker 上で自前のファインチューニング済み Gemma を立てる | ✅ 技術的には可能 | コスト・運用負担が個人運用には過大 |

このため、**ライムのキャラクター化はファインチューニングではなく Few-shot ベース**で組み立てる、という本ドキュメント全体の方針は、技術的な制約に対する合理的な答えとして位置づけられる。詳細は第9章（ファインチューニング検討条件）も参照。

#### 3.8.6 メリットの整理

| 観点 | 内容 |
| --- | --- |
| **コスト** | アイドル時0円、使った分だけ。個人運用で月数十〜数百円 |
| **運用負担** | サーバー管理ゼロ、パッチ管理ゼロ、スケーリング設定ゼロ |
| **可用性** | AWS 側で自動冗長化、SLA 提供 |
| **スケーラビリティ** | リクエスト数の変動に自動対応、突発的なバズに耐えられる |
| **開発スピード** | Lambda コード書いて `invokeModel` 呼ぶだけで使える |

## 4. 検索機能のハイブリッド戦略

### 4.1 課題：エージェント方式（Function Calling）はレイテンシが大きい

AI 自身に「検索が必要か」を判断させて検索→再推論する Agent アーキテクチャは強力だが、**推論が 2 回発生する**。

```
ユーザー: 「今の東京の天気は？」
 ↓
AI 1回目: 「これは検索が必要だな。クエリは『東京 天気』」
 ↓
システム: 検索 API 実行
 ↓
AI 2回目: 「検索結果を元にライムの口調で返答」
 ↓
出力: 「えっとね、東京は晴れみたいだよ！」
```

このため数秒〜十数秒のラグが発生し、音声合成と組み合わせると「不自然な沈黙」になる。

### 4.2 解決策：ハイブリッド構成

「ルールベースの即時判断」と「AI の自律判断」を共存させる。

#### パターン A：ファストパス（プログラムによる即時判断ルート）

- Lambda が「天気」「ニュース」「エラーコード」「MOD」「バージョン番号」等の特定キーワードを検知
- 推論前に強制的に検索 API を実行
- 検索結果をプロンプトに含めて 1 回だけ Gemma に投げる
- **メリット**: 推論 1 回で済むため圧倒的に速い

#### パターン B：エージェントパス（AI 自身による自律判断ルート）

- ファストパスをすり抜けたふんわりした質問（例：「あの空飛べるやつ、今の環境でいける？」）
- Gemma が Function Calling で「検索すべき」と判断
- Lambda が検索 API を実行 → 結果を再度 Gemma に投入 → 最終回答

#### パターン C：UX による隠蔽（つなぎの言葉）

パターン B のレイテンシをユーザーから隠す決定打。

1. Gemma から `type: "tool_call"` の JSON が返ってきた瞬間、Lambda が即座に「んー、ちょっと待ってね、今調べるから……」というつなぎセリフを Flutter へプッシュ
2. Flutter は即 VOICEVOX で再生開始
3. その音声が流れている裏で、Lambda が検索 API 実行 + 2 回目の推論を完走
4. 完成した最終回答を Flutter へプッシュ

これにより**体感の待機時間がほぼゼロ**になり、むしろ「ライムが自分で考えて調べてくれた」感が出て相棒感が増す。

### 4.3 出力 JSON スキーマ（2 パターン）

Gemma に「会話モード」と「ツール実行モード」のどちらか 1 つを選ばせる。

```javascript
const systemToolRules = `
【利用可能なツール】
あなたは必要に応じて以下のツールを使用できます。
- ツール名: "web_search"
- 目的: 最新のニュース、天気、特定のエラー解決法、MODの仕様などを調べる時に使用します。

【出力ルール（超重要）】
あなたは状況に応じて、[会話モード] または [ツール実行モード] のどちらか「1つだけ」を選び、必ず以下のJSON形式のみで出力してください。説明文や前置きは絶対に書かないでください。

パターンA：[会話モード]（通常はこちら）
自分の知識で答えられる場合や、ただの雑談、検索結果を受け取った後の最終的な返答を行う場合。
{
  "type": "chat",
  "text": "応答内容（短いセンテンス、豊富なボキャブラリー、感嘆詞を含む）",
  "emotion": "happy / sad / angry / surprised / neutral / caring",
  "intensity": 0.8
}

パターンB：[ツール実行モード]（検索が必要な時）
ユーザーの質問に答えるために、どうしても「web_search」での検索が必要だと判断した場合。
{
  "type": "tool_call",
  "tool": "web_search",
  "query": "検索エンジンに入力する具体的なキーワード（例: 'マイクラ 1.20.1 Nvidium 競合'）"
}
`;
```

### 4.4 ハイブリッド構成の強み

- 定型的な質問には爆速で答えられる（パターン A）
- 予測不能な質問にも自律的に対応できる（パターン B）
- レイテンシをユーザーに体感させない（パターン C）
- ツールを追加するだけで機能拡張できる（カレンダー、カメラ起動 など）

## 5. バックエンドアーキテクチャ（API Gateway WebSocket + Lambda）

### 5.1 なぜ WebSocket なのか

通常の REST API / HTTP API は **「1 リクエスト → 1 レスポンス → 切断」** という仕組みで、処理途中で「ちょっと待ってね」を返すことができない。

API Gateway の WebSocket API を使うと、**Lambda の処理中に何度でも Flutter にメッセージをプッシュできる**。これがハイブリッド検索戦略の前提となる。

### 5.2 全体フロー

1. Flutter アプリ起動時：API Gateway（WebSocket）に接続し、繋がりっぱなしのトンネルを作る
2. ユーザー発言：Flutter からトンネル経由で Lambda にテキストを送信
3. Lambda 処理中：トンネルを通じて「つなぎ」「最終回答」を好きなタイミングでプッシュ

### 5.3 Lambda 実装（Node.js）

```javascript
const { ApiGatewayManagementApiClient, PostToConnectionCommand } = require("@aws-sdk/client-apigatewaymanagementapi");

// WebSocket で Flutter にデータをプッシュする関数
async function sendToFlutter(endpoint, connectionId, data) {
    const client = new ApiGatewayManagementApiClient({ endpoint });
    const command = new PostToConnectionCommand({
        ConnectionId: connectionId,
        Data: Buffer.from(JSON.stringify(data))
    });
    await client.send(command);
}

exports.handler = async (event) => {
    const connectionId = event.requestContext.connectionId;
    const endpoint = `https://${event.requestContext.domainName}/${event.requestContext.stage}`;

    const body = JSON.parse(event.body);
    const userText = body.text;

    try {
        // 1. DynamoDBから設定を取得し、Gemmaに1回目の推論を投げる
        const gemmaResponse = await callGemma(userText); // 独自関数
        const responseJson = JSON.parse(gemmaResponse);

        if (responseJson.type === "tool_call") {
            // ===== 検索ルート =====

            // ① 即座にFlutterへ「つなぎのセリフ」をプッシュ
            await sendToFlutter(endpoint, connectionId, {
                type: "filler_audio",
                text: "んー、ちょっと待ってね。今調べるから……",
                emotion: "neutral"
            });

            // ② 裏で検索APIを回す（数秒かかる）
            const searchResults = await executeWebSearch(responseJson.query);

            // ③ 検索結果を元にGemmaに2回目の推論を投げる
            const secondPrompt = `検索結果: ${searchResults}\nこれを元にライムとして回答して。`;
            const finalGemmaResponse = await callGemma(secondPrompt);

            // ④ 完成した最終回答をFlutterへプッシュ
            await sendToFlutter(endpoint, connectionId, JSON.parse(finalGemmaResponse));

        } else {
            // ===== 通常ルート =====
            await sendToFlutter(endpoint, connectionId, responseJson);
        }

        return { statusCode: 200, body: 'Message processed' };

    } catch (error) {
        console.error(error);
        return { statusCode: 500, body: 'Error' };
    }
};
```

### 5.4 AWS 設定で絶対に引っかかる罠

| 項目 | 内容 |
| --- | --- |
| Lambda タイムアウト | 初期設定の **3 秒では確実に足りない**。推論 2 回 + 検索を回すなら **30 秒〜1 分** に設定。 |
| IAM 権限 | `PostToConnection` を実行するため、Lambda 実行ロールに **`execute-api:ManageConnections`** を付与。 |
| CloudWatch Logs | デバッグ用に必ず権限を付与しておく（`logs:CreateLogStream` 等）。 |
| WebSocket ルート設定 | `$connect` / `$disconnect` / `$default` / カスタムルートを忘れずに定義。 |

### 5.5 Flutter（Dart）側の受信処理

```dart
import 'dart:convert';
import 'package:web_socket_channel/web_socket_channel.dart';

final channel = WebSocketChannel.connect(
  Uri.parse('wss://あなたのAPI_GatewayのURL'),
);

// Lambda からのデータを常に待ち受け
channel.stream.listen((message) {
  final data = jsonDecode(message);

  if (data['type'] == 'filler_audio') {
    // つなぎセリフ：チャット画面には文字を出さず、音声だけ再生
    playVoicevox(data['text'], voiceId: data['voice_id']);

  } else if (data['type'] == 'chat') {
    // 最終回答：UI に吹き出し追加 + 音声再生
    addMessageToChatUI(data['text']);
    playVoicevox(data['text'], voiceId: data['voice_id']);
  }
});

// ユーザー入力の送信（プロンプトは送らない！入力文字だけ）
void sendUserInput(String text) {
  channel.sink.add(jsonEncode({"text": text}));
}
```

## 6. プロンプトをサーバー側に隠す設計上のメリット

Flutter は「テキスト送信と再生・表示のみ」、Lambda が「プロンプト組立・DB アクセス・推論・分岐」を全て担うこの構成には、3 つの強力なメリットがある。

### 6.1 アプリのアップデート不要で AI をアップデートできる

Flutter にプロンプトを書いてしまうと、ライムの口調や Few-shot を変えるたびに **アプリのビルド・配布**が必要になる。

Lambda / DynamoDB 側に持たせておけば、**AWS 上のテキストを書き換えるだけで次の会話から即反映**される。

### 6.2 通信量が減り、レスポンスが速くなる

毎回数千文字のシステムプロンプトをスマホからネットワーク越しに送信するのは無駄。Flutter からはユーザー入力テキストだけを身軽に送り、重いプロンプトは AWS 内部の高速ネットワークで結合する方が圧倒的に効率的。

### 6.3 プロンプト（キャラクターの「魂」）が盗まれない

アプリにプロンプトをハードコーディングしていると、ソースコードを解析（リバースエンジニアリング）された時にキャラクター設計が丸裸になる。サーバー側に隠せばブラックボックス化でき、漏洩・流用を防げる。

### 6.4 役割分担まとめ

| 主体 | 責務 |
| --- | --- |
| Flutter | 「ユーザーが『なんか疲れた』って言ってるよ！Lambda さん、あとはよろしく！」 |
| Lambda | 「了解！ DB からライムの性格データを引っ張ってきて、プロンプトを合体させて、Gemma に推論させて返すね！」 |

「見た目・操作（フロントエンド）」と「ロジック・データ（バックエンド）」を完全に切り離す設計は、ソフトウェア開発の理想的な構造に沿っている。

## 7. ローカルテスト環境（Ollama + Tailscale + Node.js）

### 7.1 構成のマッピング

本番 AWS 構成をローカルで模倣することで、**課金せずに同じアーキテクチャを検証できる**。

| 本番（AWS） | ローカル（代替） |
| --- | --- |
| API Gateway WebSocket | Node.js `ws` ライブラリで立てる WebSocket サーバー |
| Lambda（ロジック） | Node.js のサーバープロセス |
| DynamoDB（プロンプト保存） | Node.js 内の変数 or SQLite |
| 推論エンドポイント（Bedrock 等） | ローカル Ollama（`http://localhost:11434`） |
| ネットワーク到達性 | Tailscale で端末間を直結 |

### 7.2 セットアップ

```bash
mkdir raim-local && cd raim-local
npm init -y
npm install ws node-fetch
# Node.js v18 以降なら node-fetch は不要（標準 fetch が使える）
```

### 7.3 サーバーコード（`server.js`）

```javascript
const { WebSocketServer } = require('ws');

const wss = new WebSocketServer({ port: 8080 });

// サーバー側に隠し持つライムのシステムプロンプト
const systemPrompt = `
あなたはライムです。一人称は私、二人称はあなた。
以下のJSON形式のみで返答してください。
{"type": "chat", "text": "応答内容", "emotion": "happy"}
`;

wss.on('connection', function connection(ws) {
  console.log('Flutterアプリが接続しました');

  ws.on('message', async function message(data) {
    const userMessage = JSON.parse(data).text;
    console.log('受信:', userMessage);

    // 即座につなぎセリフを返す
    ws.send(JSON.stringify({
      type: "filler_audio",
      text: "んー、ちょっと待ってね……",
      emotion: "neutral"
    }));

    try {
      // 裏でローカル Ollama に推論させる
      const ollamaResponse = await fetch('http://127.0.0.1:11434/api/chat', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
          model: "gemma3:12b", // 実際のOllamaのモデル名に合わせる
          messages: [
            { role: "system", content: systemPrompt },
            { role: "user", content: userMessage }
          ],
          stream: false
        })
      });

      const ollamaData = await ollamaResponse.json();
      const aiText = ollamaData.message.content; // Gemma が生成した JSON 文字列

      ws.send(aiText);

    } catch (error) {
      console.error("Ollama エラー:", error);
    }
  });
});

console.log('ローカル中継サーバー起動: ws://localhost:8080');
```

### 7.4 起動

```bash
node server.js
```

### 7.5 Flutter からの接続（Tailscale 経由）

Node.js / Ollama が動いている PC の Tailscale IP（`100.x.y.z`）を Flutter から指定。

```dart
final channel = WebSocketChannel.connect(
  Uri.parse('ws://100.x.y.z:8080'),
);

channel.sink.add(jsonEncode({"text": "マイクラのサーバー重いんだけど"}));
```

### 7.6 このローカル環境で検証できること

- Flutter でテキストを送信 → 瞬時に `type: "filler_audio"` が返ってきて再生開始
- 裏で Ollama の GPU（RTX 4070 等）が動き出して推論
- 数秒後、Ollama の推論が完了 → 最終回答（JSON）が Flutter に届いて表示
- **WebSocket の挙動・つなぎ言葉の UX・プロンプトのチューニングを実際の AWS と同じロジックで確認できる**

これが完璧に動くようになったら、Node.js のコードをそのまま Lambda に移植し、Ollama の URL を Bedrock / SageMaker 等に差し替えるだけで本番化できる。

## 8. Lambda 処理の高速化テクニック

### 8.1 並列処理（`Promise.all`）

Gemma 推論前の準備（プロンプト組立・履歴取得・検索）を**直列ではなく並行**に走らせる。

```javascript
const [history, fewShots, searchResult, userState] = await Promise.all([
  fetchHistoryFromDynamoDB(userId),       // タスクA: 会話履歴
  fetchSceneFewShots(detectedScene),       // タスクB: シーン別 Few-shot
  needsSearch(userText) ? executeWebSearch(extractQuery(userText)) : null, // タスクC: 必要なら検索
  fetchUserState(userId)                   // タスクD: ユーザー状態
]);

// すべて完了したら結合して Gemma に投入
const prompt = buildPrompt({ history, fewShots, searchResult, userState, userText });
const response = await callGemma(prompt);
```

これらが完了するのは数 ms 〜 数百 ms オーダー。直列だと累積で 1 秒近くなることもある。

### 8.2 ストリーミング応答

テキストが完成するまで待たず、生成された文字から順次 Flutter に送りつける。

- API Gateway WebSocket でチャンク単位（句読点で区切る等）に送信
- Flutter 側でチャンクごとに VOICEVOX に投入して再生開始
- **体感の待機時間は「最初の数文字が生成されるまでの時間」だけ**になる

### 8.3 思考の分離（裏でエージェントを走らせる）

会話のテンポを絶対に崩したくない場合の究極系。Lambda の中で処理を 2 ルートに分ける。

#### 即答ルート
Gemma に「会話の返答」だけをサクッと作らせて即返す。
例：「あ、そのエラーね！ちょっと待って、今ログの解決策調べるから！」

#### 思考ルート
同じ Lambda 内で非同期に重い推論（検索エージェント等）を走らせる。完了したら追撃で WebSocket メッセージを送信。
例：「わかった！あのエラーはね……」

→ ライムが**本当に「自分の意思で調べて、わかったタイミングで話しかけてきた」ように見える**。

## 9. ファインチューニングの検討条件と今後のロードマップ

### 9.1 FT を検討すべき「壁」と現実的な制約

ファインチューニングが必要になるとすれば、それは「ボキャブラリー不足」ではなく、以下の壁にぶつかった時。

- **レイテンシ**: プロンプトが長すぎて毎回の推論レスポンスが許容できなくなった
- **コスト**: 入力トークン数が膨らみすぎて運用費が現実的でなくなった
- **指示忘却**: プロンプトの中央部の指示を Gemma が頻繁に取りこぼすようになった

「今の長いプロンプトと同等のキャラクター性を、設定文なし（短いプロンプト）で瞬時に引き出したい」となった時、初めて FT の価値が生まれる。

#### 9.1.1 重要な制約：Gemma 3 は Bedrock カスタムモデルインポート非対応

Bedrock Custom Model Import は Llama 系・Mistral 系などをサポートするが、**Gemma アーキテクチャはインポート非対応**。これにより、もしファインチューニングを実施したとしても、Bedrock のサーバーレス API（`google.gemma-3-12b-it`）には乗せられない。

ファインチューニング後の Gemma 3 を本番運用する選択肢は以下のみ：

| 選択肢 | コスト感 | 運用負担 |
| --- | --- | --- |
| SageMaker エンドポイントで自前ホスト | インスタンス時間課金（立てっぱなしで月数万〜数十万円） | 中（AWSフルマネージドだが運用設定は必要） |
| EC2 + GPU で自前推論サーバー | インスタンス時間課金 + 運用工数 | 大（OS・ライブラリ・スケーリング自前管理） |
| 他社推論サービス（Replicate / Modal 等） | 従量課金（但しコールドスタートあり） | 小〜中 |

→ いずれもサーバーレス Bedrock の「使った分だけ・月数百円」というコスト感とは桁が違う。**個人運用では現実的に選択肢にならない**。

### 9.2 当面の方針（確定）

#### 戦略

**ファインチューニングは採用しない。Few-shot + 動的シーン判定（Embedding） で完結させる。**

理由：
- Gemma 3 はカスタムモデルインポート非対応のため、FT 後の本番運用が事実上不可能
- そもそも Gemma 3 12B IT は表現力が高く、Few-shot + Embedding ベースのシーン判定でキャラクター性は十分に出せる（第1章・3.6 で詳述）
- Few-shot の追加だけでボキャブラリー拡張ができ、しかも本番運用コストは数百円規模

#### 実行ロードマップ

1. **ローカル検証フェーズ**（現在）
   - Ollama + RTX 4070 で `gemma3:12b` 起動
   - Few-shot 入りプロンプトでキャラクター性を確認
   - bge-m3 等で Embedding シーン判定を実装・検証
   - Node.js WebSocket 中継サーバーで UX フローを検証

2. **シーン熟成フェーズ**
   - `scenes/*.json` を 5〜10 シーンから始め、運用しながら拡張
   - Few-shot を 50〜100 例規模に増やしてもキャラが崩れないかを実証

3. **AWS 移行フェーズ**
   - Lambda + API Gateway WebSocket + DynamoDB をプロビジョニング
   - Bedrock サーバーレスで `google.gemma-3-12b-it` と `amazon.titan-embed-text-v2:0` を有効化
   - `scenes-embedded.json` を Titan で再ビルド
   - Node.js のコードをそのまま Lambda に移植、`MODE=aws` に切り替え

4. **本番運用フェーズ**
   - 月数百円規模で運用開始
   - シーン追加・Few-shot 拡張を継続的に実施
   - 必要に応じてマルチモーダル（10章）、長期記憶等を追加

### 9.3 拡張アイデア

- ツール拡張: カレンダー登録、カメラ起動、スマートホーム操作、画像生成 等
- 「ライム側から突然話しかけてくる」プッシュ通知的機能（WebSocket 常時接続を活用）
- Live2D / StreamDiffusion との連動（感情パラメータをアバター表情に反映）
- 長期記憶: 重要な会話を要約して別テーブルに保存し、必要に応じて参照

### 9.4 検証の優先順位

| 優先度 | 検証項目 | 目的 |
| --- | --- | --- |
| 高 | Few-shot 入りプロンプトで「しずく」的なボキャブラリーが出るか | キャラクター成立の確認 |
| 高 | Node.js + Ollama でつなぎ言葉 UX が成立するか | 体感レイテンシの実証 |
| 高 | Embedding でシーン判定が機能するか（5シーン程度で実験） | 動的 Few-shot 選択の精度確認 |
| 高 | Few-shot を 50 例〜100 例規模に拡張してもキャラが崩れないか | 大量化戦略の実証 |
| 中 | Function Calling で `tool_call` JSON が安定して出るか | ハイブリッド検索戦略の前提 |
| 中 | プロンプト圧縮の限界点（どこまで削るとキャラが崩れるか） | 動的プロンプト設計の指標 |
| 低 | DynamoDB のシーン判定ロジック実装 | 動的プロンプト本実装 |
| 低 | ストリーミング応答の実装 | さらなる体感速度向上 |

## 10. 将来の拡張：マルチモーダル化・時間認識・状況認識

ライムをさらに「相棒らしく」していくための拡張軸。いずれも本ドキュメントが扱う「AI をどう良くするか」の方向性として将来検討する。

### 10.1 マルチモーダル化（カメラ・画像入力）

ユーザーの状況をテキストだけで判定するのには限界がある。カメラから画像を取り込み、ライムが「視覚的に状況を把握する」ことで、応答の精度と親密度が大幅に上がる。

#### 想定ユースケース

- 「これ何？」とユーザーが何かを見せる → ライムが認識して反応
- 食事の写真を見せる → 「美味しそう！何作ったの？」など共感
- 部屋の様子から状況推測 → 「散らかってきたね、片付け手伝う？」
- ユーザーの表情を読み取り → 元気そう／疲れていそうを判断して口調調整
- ホワイトボードや画面のスクショから技術的な質問 → エラー画面を見て一緒にデバッグ

#### 技術選択肢

| アプローチ | 内容 | 適合度 |
| --- | --- | --- |
| マルチモーダル対応 LLM | Gemma 3 自体が画像入力対応モデル。プロンプトと一緒に画像を投げて統合的に応答可能 | **本命**。Gemma 3 12B IT は画像入力対応 |
| 画像 → テキスト変換 + 既存 LLM | 画像から説明文を生成し、それをテキストとして既存パイプラインに流す | フォールバック案。シンプルだが情報損失あり |
| Vision 専用モデル + LLM 連携 | YOLO 等の検出器でオブジェクト認識し、結果を LLM プロンプトに含める | 特定タスク（物体検出、感情認識）に強い |

Gemma 3 がそもそも画像理解できるため、**入力チャネルを増やすだけで実現可能**。会話履歴に画像も含めて管理する設計に拡張する。

#### Embedding 戦略への影響

将来は **画像 Embedding** も同じ空間で扱える（CLIP のようなマルチモーダル埋め込みモデルを使う）。「夜の暗い部屋」「散らかった机」「料理の写真」などの状況も Embedding 化して、それに応じたシーン（`late_night`, `cooking` 等）を判定する、という拡張が可能。

### 10.2 時間認識（時刻・曜日・季節による反応変化）

人間の友達なら「朝だね、おはよう」「もう深夜じゃん、早く寝な？」「今日は土曜だから一日遊べるね」みたいに時間を意識して話す。ライムにもこれをやらせたい。

#### 実装方針

サーバー側でユーザー発言ごとに時刻を付与してプロンプトに含める。

```
[コンテキスト]
- 現在時刻: 2026年6月15日(日) 02:34
- 曜日: 日曜日（深夜）
- 季節: 初夏
- 直前の会話: ユーザーは1時間前にも会話していた
```

これがプロンプトに含まれるだけで、Gemma 3 は時間文脈を踏まえた応答ができるようになる。

#### 時間ベースの動的シーン候補

| シーンID | トリガー | 想定する応答 |
| --- | --- | --- |
| `early_morning` | 5〜7時 | 「おはよう、早起きだね」 |
| `late_night` | 24〜4時 | 「もう深夜だよ？無理しないでね」 |
| `weekend` | 土日 | 「今日は休み？何して過ごす？」 |
| `monday_blues` | 月曜朝 | 「月曜だ……一週間始まったね。一緒に頑張ろう」 |
| `birthday` | ユーザー誕生日 | 「お誕生日おめでとう！」 |

これらは Embedding ベースのシーン判定とは別に、**時刻ルールでシーンを上書き／追加**できるようにする。

### 10.3 状況認識（位置情報・カレンダー・センサー連携）

時間と並んで、「ユーザーが今何をしているか」を文脈として取り込めば、さらに応答が立体的になる。

#### 取り込めるシグナル

- **位置情報**：自宅 / 学校 / 通学中 / 外出先
- **カレンダー連携**：「次の予定までの時間」「今日の予定の内容」
- **PC のアクティビティ**：開発中（VS Code / IDE 起動中）、ゲーム中、動画視聴中
- **ヘルスデータ連携**：睡眠時間、心拍数（疲労度推定）
- **天気**：晴れ／雨／猛暑日／寒波

#### Embedding 戦略への影響

これらシグナルもすべて「状況コンテキスト」としてプロンプトに含められる。さらに、シーン判定の特徴量として使うこともできる：

- 「夜 + 自宅 + コーディング中」→ `late_night_dev` シーン → 「お、まだ作業中？コーヒー入れたら？」
- 「朝 + 通学中 + テスト前日」→ `commute_pre_exam` シーン → 「テスト頑張ってね！復習する？」

### 10.4 長期記憶（重要な会話の永続化）

会話履歴の TTL 削除（3.5）は短期記憶。長期記憶として、ライムに **「ユーザーについての知識」を蓄積させる**設計も将来検討する。

- ユーザーの趣味、好きなゲーム、好きな食べ物、家族構成、目標
- 過去のエピソード（「あの卒研発表で頑張ったやつ」など）
- 会話の中でライムが学習した「相棒としての知識」

これらを別テーブル（あるいはベクトルDB）に保存し、関連する話題が出た時に Embedding ベースで検索して引き出す。**長期記憶の検索も Few-shot 選択と同じ Embedding 基盤の上に乗せられる**ため、3.6 で構築する仕組みがそのまま再利用できる。

### 10.5 ライムから話しかける（プロアクティブ会話）

ユーザーが話しかけなくても、ライム側から会話を開始する仕組み。WebSocket 常時接続を活用できる。

- 朝の挨拶（毎朝決まった時間に「おはよう」と話しかける）
- カレンダー連動（予定の30分前にリマインド）
- 異変検知（普段より無口、深夜まで起きている → 「大丈夫？」）
- ニュース話題提供（ユーザーの興味分野で大きなニュースが出たら共有）

これも時間認識・状況認識の応用。ライムが「相棒」として能動的に存在感を持つための機能。

## 付録 A：用語整理

| 用語 | 意味 |
| --- | --- |
| Few-shot prompting | プロンプト内に対話例を複数含めることで、モデルに望ましい出力スタイルを学習させる手法 |
| Function Calling | LLM が「ツールを使うべき」と判断したとき、構造化された JSON で関数呼び出しを要求する仕組み |
| Lost in the middle | 長いプロンプトの中央部の情報をモデルが取りこぼす現象 |
| TTL (Time to Live) | DynamoDB の自動データ削除機能。指定時刻を過ぎたアイテムを自動的に消す |
| WebSocket | サーバー・クライアント間で双方向の通信を維持できるプロトコル |
| `PostToConnection` | API Gateway WebSocket で接続中クライアントにサーバーからメッセージを送る API |
| Embedding | 文章を意味を保ったまま数値ベクトルに変換する技術。意味が近い文章はベクトルが近くなる |
| 埋め込みモデル (Embedding model) | Embedding を生成するための専用モデル。生成LLM と比べて小さく速い（数百MB、数十ms） |
| コサイン類似度 | 2 つのベクトルがどれくらい同じ方向を向いているかを -1〜+1 で表す指標。Embedding 同士の意味の近さに使う |
| Centroid（重心ベクトル） | あるシーンの代表セリフを Embedding 化して平均を取ったベクトル。シーン判定の基準点 |
| 動的 Few-shot 選択 | ユーザー発言ごとに最も近いシーンの Few-shot だけを差し込むテクニック。トークン量を一定に保ちつつボキャブラリーを拡張できる |
| マルチモーダル LLM | テキストだけでなく画像・音声等の複数モダリティを入力として扱える LLM。Gemma 3 は画像入力対応 |
| 正規化（normalize） | ベクトルの長さを 1 に揃える処理。コサイン類似度計算が単純なドット積になり、モデル間でも比較しやすくなる |
| MTEB | Massive Text Embedding Benchmark。Embedding モデルの性能評価ベンチマーク |

## 付録 C：Embedding モデル互換性と移行時の注意

3.6 で導入する Embedding は、ローカル開発と AWS 本番で**同じモデルを使えない**ため、互換性に注意が必要。本付録はその設計指針をまとめる。

### C.1 Bedrock Titan Embeddings v2 はローカルで動かせない

Titan Embeddings v2 は Amazon Bedrock 専用のクラウドサービスで、モデル重みは非公開。Hugging Face にある `amazon/Titan-text-embeddings-v2` は性能スコア（MTEB ベンチマーク）と使用例のリポジトリで、推論可能なモデル本体ではない。

AWS 公式評価でも Titan は「フルマネージドのクラウド専用サービス」と明言されており、ローカル推論やオンプレデプロイには使えない。**「Titan をローカルで動かす」という選択肢は存在しない**。

### C.2 「同じものは無理」だが「動作を同等にする」は可能

ローカルでは、Titan v2 と **次元数・正規化・言語対応** を揃えたオープンモデルを使う。完全互換ではないが、シーン判定の挙動を同等にできる。

#### 揃えるべき仕様

| 観点 | Titan v2 の仕様 | ローカル側で揃えるべき値 |
| --- | --- | --- |
| 出力次元 | 1024 / 512 / 256（選択可） | **1024 で固定推奨**（精度重視） |
| 正規化 | `normalize=true` で単位ベクトル化 | **正規化前提でコサイン類似度計算** |
| 言語対応 | 100以上の言語事前学習 | 日本語精度高めのモデル必須 |
| 最大入力 | 8,192トークン | Few-shot 例文程度なら問題なし |

### C.3 ローカル代替モデル候補（Ollama で動作）

RAiM は日本語キャラなので、**日本語精度と Titan 互換次元（1024）** を両立できるモデルを選ぶ。

| モデル | 次元数 | 日本語 | サイズ | 評価 |
| --- | --- | --- | --- | --- |
| **bge-m3** | 1024 | ◯（100以上の言語対応） | 約 2.3GB | **本命**。Titan に思想が近い |
| **snowflake-arctic-embed2** | 1024 | ◯（多言語対応） | 約 1.2GB | 軽量で高精度 |
| mxbai-embed-large | 1024 | △（英語強） | 670MB | 英語中心なら最有力 |
| nomic-embed-text | 768 | △ | 274MB | **次元数が合わず非推奨** |

RTX 4070 12GB なら Gemma 3 12B（約 8GB）と bge-m3（約 2.3GB）の同居は余裕。

### C.4 異なるモデル間のベクトル互換性は**ゼロ**

これが最重要の落とし穴。同じ文章でも、別の Embedding モデルでは全く違うベクトルが返ってくる。

```
"疲れた" を bge-m3 で計算   → [0.12, -0.45, 0.78, ...]
"疲れた" を Titan v2 で計算 → [0.31,  0.08, -0.22, ...]   ← 全然違う
```

数値が違うだけでなく、ベクトル空間そのものが別物なので、片方で計算したベクトルを他方の空間で比較するのは無意味。

#### 何を再ビルドする必要があるか

ローカル → 本番への移行時に必須の作業：

| データ | 流用可能か | 理由 |
| --- | --- | --- |
| `scenes/*.json`（生データ） | ✅ そのまま流用可 | テキストなのでモデル非依存 |
| Few-shot 対話例 | ✅ そのまま流用可 | テキストなのでモデル非依存 |
| `scenes-embedded.json`（埋め込み済みベクトル） | ❌ **再ビルド必須** | モデル変更でベクトルが別物に |

移行手順は概念的にはシンプル：

1. ローカルで scenes/*.json を熟成（Few-shot を増やす、表現を磨く）
2. ローカルの bge-m3 で動作確認、シーン判定が機能していることを検証
3. 本番デプロイ時に、Titan v2 で scenes-embedded.json を**1回だけ再生成**
4. 以後、scenes/ 側を更新するたびに本番でも再生成スクリプトを叩く

### C.5 正規化（normalize）の重要性

コサイン類似度を扱う際、**ベクトルが単位ベクトル（長さ1）に正規化されているかどうか**は計算結果と挙動に影響する。

#### 正規化されたベクトル同士の利点

- コサイン類似度の計算が単純なドット積になる（割り算不要）
- ベクトル長さの違いに左右されず、純粋に方向（意味）だけで類似度を測れる
- スレッショルド（閾値）の値が安定する（モデル間でも比較しやすい）

#### 揃え方の方針

- **Titan 側**：`normalize: true` パラメータを渡せばAWSが正規化済みベクトルを返す
- **Ollama 側**：返ってくるベクトルが正規化されているかはモデル依存（多くは正規化されているが保証はない）

→ どちらの環境でも、Embedding 取得後に必ずコード側で正規化処理を入れて、確実に揃える方が安全。

### C.6 互換性チェックの運用ルール

Embedding 周りで事故らないための運用ルール：

| ルール | 目的 |
| --- | --- |
| `scenes-embedded.json` のヘッダに `dim` と `model_id` を埋め込む | 起動時にバリデーション、不一致なら起動失敗 |
| モデル変更時は必ず再ビルドスクリプトを実行 | ベクトル互換性の確保 |
| 次元数を揃える（ローカル 1024 ⇔ Titan 1024） | スコープ統一 |
| 取得後に必ず正規化処理を通す | 単位ベクトル化の保証 |
| しきい値（cosine 0.7 など）はモデル変更時に再キャリブレーション | モデル間でしきい値の体感が変わるため |

### C.7 結論：開発フェーズと本番フェーズの整理

| フェーズ | 推奨 Embedding | コスト感 |
| --- | --- | --- |
| ローカル開発・検証 | bge-m3（Ollama） | 電気代のみ、推論無料 |
| AWS 本番 | Titan Embeddings v2（1024次元、normalize=true） | 100万トークン $0.02、月数円〜数十円規模 |

「ローカルでロジックと熟成」「本番は使った分だけ課金」という構成が成立する。Embedding に関しては、Titan の API 一発呼び出しと従量課金の組み合わせがコスト効率上の優位を発揮する領域。

### C.8 生成LLM はローカル ⇔ 本番で「実質同一モデル」が使える（朗報）

Embedding と異なり、**生成LLM（Gemma 3 12B IT）はローカルと AWS で同じモデルを使える**。これにより、ローカルで動作確認したプロンプトの挙動が本番でほぼそのまま再現される。

| 環境 | 実体 | モデル名 |
| --- | --- | --- |
| ローカル（Ollama） | Google 公式の Gemma 3 12B IT オープンウェイト | `gemma3:12b` |
| AWS 本番（Bedrock サーバーレス） | Google 公式の Gemma 3 12B IT オープンウェイト | `google.gemma-3-12b-it` |

両方とも **Google が公開している同じウェイトを使っているため、応答の傾向、Few-shot への反応、口調の再現性は実質一致** する。Embedding と違って次元数の不整合や再ビルド要件といった問題は発生しない。

#### 推論バックエンド側で気にすべきわずかな差分

| 観点 | Ollama（ローカル） | Bedrock（本番） |
| --- | --- | --- |
| 推論エンジン | llama.cpp ベース | AWS 独自最適化 |
| デフォルトパラメータ | エンジン依存 | API デフォルト |
| 量子化 | 設定可能（GGUF Q4_K_M 等） | 不明（おそらく FP16 相当） |
| レイテンシ | RTX 4070 で 数秒 | Bedrock で 数百ms〜数秒 |

量子化レベルの違いで微妙にニュアンスが変わることはあるが、キャラクターの大枠は崩れない。ローカル検証で十分にチューニングしたプロンプトが、本番でほぼそのまま動く。

#### 結論：ライムの場合の互換性まとめ

| データ・モデル | ローカル ⇔ 本番の互換性 | 移行時の対応 |
| --- | --- | --- |
| `scenes/*.json`（生データ） | ✅ 完全互換 | そのままコピー |
| Few-shot 対話例 | ✅ 完全互換 | そのままコピー |
| 生成LLM 自体（Gemma 3 12B IT） | ✅ 実質同一 | モデルID を差し替えるだけ |
| Embedding モデル | ❌ 別物（bge-m3 ⇔ Titan v2） | `scenes-embedded.json` を再ビルド |

**気をつけるべきは Embedding ベクトルだけ**。これ以外は実質ローカルで作ったものがそのまま本番で動く設計が成立する。
