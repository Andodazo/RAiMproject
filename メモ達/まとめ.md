# RAiM 技術設計まとめ

## プロジェクト概要

**プロジェクト名**: RAiM（i のみ小文字、読み: ライム）
**種別**: AIコンパニオンアプリ（卒業制作）
**参考**: AI VTuber「しずく」のような、3Dキャラクターと自然な対話ができるAIコンパニオン
**最終リリースターゲット**: Windows / iOS / Android

---

# Part 1: プロトタイプ仕様（現在の到達点）

## プロトタイプで実現したこと

- **実LLM接続**: Gemma 3 12B IT（ローカル Ollama 経由）
- **会話履歴対応**: 直近10往復を毎回送信、文脈を保てる
- **感情パラメータ取得**: 応答JSONから emotion/intensity を取得
- **Unity 連携**: WebSocket で立ち絵5枚を表情切り替え
- **Windows GUI**: 参考UI風レイアウト（背景画像+キャラ+チャットオーバーレイ）
- **音声合成**: VOICEVOX（春日部つむぎ）でライムの応答を読み上げ
- **プラットフォーム抽象化**: Windows/iOS/Android で実装を切り替えできる設計
- **Tailscale 連携**: 学校から自宅PCの Ollama を VPN 経由で叩く準備

## 技術スタック

| 領域 | ライブラリ/ツール |
|---|---|
| UI | Flutter (Dart) |
| 3D/2D描画 | Unity 2022 LTS（SpriteRenderer で立ち絵切替） |
| LLM | Ollama + Gemma 3 12B IT（ローカル実行） |

| VPN | Tailscale（学校↔自宅） |

## プロトタイプのデータフロー

ユーザーが「おはよう」と入力した時の処理：

```
[Flutter UI] ChatInput → ChatProvider.sendUserMessage()
   ↓
[ChatProvider] 履歴+入力をLLMServiceに渡す
   ↓
[OllamaService] http://localhost:11434/api/chat に POST
   ↓
[Ollama / Gemma 3 12B IT] 推論
   ↓ {"text":"おはよう！","emotion":"happy","intensity":0.8}
   ↓
[ChatProvider] 履歴に追加、UI再描画
   ├→ [UnityCommunicator] Unity に WebSocket送信 → 立ち絵が happy に切替
   └→ [TTSService] VOICEVOX で読み上げ → 春日部つむぎの声で「おはよう！」
```

## プラットフォーム別の実装切り替え

抽象化レイヤー `UnityCommunicator` で、プラットフォームごとに通信方式が違う：

```
ChatProvider
    ↓ UnityCommunicator（抽象インターフェース）
    ├─ WindowsUnityBridge（WebSocket、Windows用）
    └─ EmbedUnityBridge（sendToUnity、iOS/Android用）
```

main.dart でプラットフォーム自動判定して実装を選択。**ChatProvider は具体実装を知らない**。これにより、Flutter コードの大半が全プラットフォームで共通。

# Part 2: 本番移行で必要なこと

## 本番化の全体像

プロトタイプの**ローカル完結構成**を、**クラウド経由構成**に変換する。
コードベースの大部分はそのまま流用、足りない部分を追加実装。

## 本番化で追加実装が必要なもの

### 1. AWS バックエンド（Lambda + API Gateway）

**目的**: APIキー隠蔽、プロンプト保護、レート制限

**実装**: Lambda関数（100行程度）、API Gateway設定、IAMロール

### 2. ユーザー認証（AWS Cognito）

**目的**: 会話履歴の個別管理、不正利用防止

**実装**: Cognito User Pool、Flutter認証フロー、JWT管理

### 3. 会話履歴の永続化（DynamoDB）

**目的**: アプリ再起動後も会話継続、長期記憶

**実装**: DynamoDBテーブル設計、Lambda経由の保存・取得

### 4. エラーハンドリングの強化

ネット切断、APIタイムアウト、JSON崩れのリトライ、ユーザーフレンドリーなエラー表示

### 5. セキュリティ対策

HTTPS強制、入力サニタイズ、レート制限、不正利用検知

### 6. キャラの完成度向上（プロンプトエンジニアリング主軸）

**方針確定: ファインチューニングは行わず、プロンプト + few-shot で性格構築**

- システムプロンプトに口調サンプル・応答例を10件以上組み込む（few-shot）
- 性格3パターン（A/B/C）の最終決定と評価
- temperature / top_p のチューニング
- ガードレール設定（NGワード、不適切応答防止）

**ファインチューニングをしない理由**:
- AWS担当者助言: 「コンパニオン用途ならプロンプトで十分」
- 反復速度: プロンプト変更は即時、ファインチューニングは数時間〜数日
- 透明性: なぜその応答になったか説明可能（卒研での説明責任）
- コスト: 学習コスト・データ準備工数を本番品質向上に振り向ける

**将来の選択肢として残すもの**:
- 卒研後の発展課題として LoRA/QLoRA 学習を検討
- ただし Gemma 3 は Bedrock Custom Model Import (CMI) 非対応のため、ファインチューニング版を Bedrock 管理で動かすことは不可
- やる場合: SageMaker ホスティング または Llama系/Qwen系へのアーキ変更が必要

### 7. RAG（検索機能）

- OpenSearch Serverless でベクトル検索
- 会話履歴とキャラ設定資料のベクトル化
- 関連情報をプロンプトに混ぜる

### 8. Unity 統合（プラットフォーム別）

- **iOS/Android**: flutter_embed_unity でエクスポート → Xcode/Android Studio で統合
- **Windows**: flutter_embed_unity非対応のため、Flutter単体で立ち絵表示 + Unity別ウィンドウのハイブリッド

### 9. アプリパッケージング

- **Windows**: インストーラ作成
- **iOS**: .ipa生成、Apple Developer登録、App Store審査
- **Android**: .apk/.aab生成、Google Play Developer登録、Play審査

### 10. STT（音声入力）

sherpa-onnx を Flutter に統合、マイク権限処理

### 11. TTS の本番化

プロトタイプの VOICEVOX → 本番では uPiper（Unity内部統合、オフライン動作）または商用サービス

### 12. キャラ画像の作り込み

- **現状**: 表情差分5枚（透過済み）
- **本番**: 表情細分化、ポーズバリエーション、Live2D化、口パク用差分

# Part 4: 主要な技術選定とその理由

## Flutter + Unity の組み合わせ

- Flutter: TypeScript/Reactスキルが活きる、UI開発が圧倒的に楽
- Unity: 3D/2Dキャラ描画のプロ向けエンジン、VRChat改変経験が活きる

## Flutter ⇔ Unity 統合方式（プラットフォーム別）

**iOS/Android**: flutter_embed_unity（公式安定、参考UI通り統合可能）

**Windows**: flutter_embed_unity 非対応、検証で判明：
- `flutter_unity_widget_2` も Windows 非対応
- `flutter_native_view` はメンテ止まり、ビルドエラー（std::chrono問題）
- `flutter_embed_unity` も Windows 非対応 + Androidエミュレータ非対応

→ **Windows では Flutter 単体で立ち絵表示 + Unity 別ウィンドウ表示のハイブリッド方式**を採用

## 通信方式

- **Windows**: WebSocket（Flutterサーバー、Unityクライアント）
- **iOS/Android**: flutter_embed_unity の sendToUnity（プロセス内通信）

抽象化レイヤー `UnityCommunicator` で実装を切替

## LLM: Gemma 3 12B IT

**ローカル開発・本番ともに同一モデルを採用**（モデル切り替えコスト・プロンプト調整コストをゼロ化）

### ローカル開発（Ollama）
- `ollama pull gemma3:12b`（約8GB）
- RTX 4070 で快適に動作、Tailscale 経由で学校PCからも叩ける

### 本番（AWS Bedrock 管理モデル）
- **モデルID**: `google.gemma-3-12b-it`
- **エンドポイント**: `bedrock-mantle`（推奨）または `bedrock-runtime`
- **料金**: 入力 $0.09/M トークン、出力 $0.29/M トークン（従量課金）
- **コンテキスト**: 128K トークン、最大出力 8K
- **対応API**: Converse / Invoke / Chat Completions（全部対応）
- **東京リージョン対応**: `ap-northeast-1`
- **マルチモーダル**: テキスト + 画像入力対応（JPEG/PNG/GIF/WebP）

### 選定理由（班員向け説明用）
- **日本語性能が強い**: 140以上の言語対応、Gemini 2.0 トークナイザーでアジア言語のエンコーディング改善
- **画像入力対応**: 同モデルでマルチモーダル、後でVLモデルへ切替不要
- **コスト効率**: Qwen3 32B より入力60%安、出力52%安
- **ローカル⇔本番完全互換**: 開発時と本番で同じモデル、プロンプト調整やり直し不要
- **API豊富**: Converse API 対応（Qwen3 系は非対応）
- **AWS担当者推奨**: ライム用途で最適と確認済み

### 制約事項
- **Bedrock Custom Model Import (CMI) 非対応**: Gemma アーキは CMI 対象外。ただし**今回はファインチューニング非実施**のため実害なし

## AWS Bedrock を本番LLM基盤に

- **Gemma 3 12B IT を管理モデル（マネージド）として利用**、サーバーレス・従量課金
- インフラ管理不要、自動スケール、5分間アイドルでスケールゼロ
- Project Mantle エンドポイント（`bedrock-mantle`）で配信
- ガードレール、エージェント、Knowledge Base、Flows などのBedrock機能を組み合わせ可能
- 東京リージョン対応で低レイテンシ

### Bedrock 機能の活用予定
- **Standard 階層**: pay-per-token の通常利用
- **Flex 階層**: バッチ処理など即時応答不要な場合に50%割引
- **Guardrails**: 不適切応答のフィルタリング
- **Converse API**: ツール呼び出し、構造化出力、画像入力に対応

## TTS の戦略

- **プロトタイプ**: VOICEVOX（春日部つむぎ、無料、ローカル動作、可愛い声）
- **本番**: uPiper（オンデバイス、Unity 内部統合）または商用サービス

## Tailscale で自宅PC ↔ 学校PC を VPN接続

- 自宅デスクトップの Ollama を学校のノートPCから叩ける
- baseURL を変えるだけで切り替え可能

# Part 5: Windows 統合の技術調査結果

プロトタイプ段階で「Windowsで参考UI通りに Flutter UI内に Unity を埋め込む」ことを検証した結果、**現状の Flutter エコシステムでは実現困難**であることが判明。

## 検証した方法と結果

| 方法 | 結果 |
|---|---|
| flutter_unity_widget | ❌ Windows非対応（公式表明） |
| flutter_unity_widget_2 | ❌ Windows非対応 |
| flutter_embed_unity | ❌ Windows非対応、Androidエミュレータでも動作不可（公式表明） |
| flutter_native_view | ❌ メンテ停止、ビルドエラー（std::chrono問題） |
| Win32 API 自前実装 | △ 技術的に可能、卒研期間では困難 |
| Unity WebGL + webview_windows | △ 未検証、パフォーマンス懸念 |

## なぜ難しいか

Flutter の PlatformView 機能が Windows デスクトップで未サポート。これは Google のロードマップ依存で、卒研期間内では解決見込みなし。

## だから本番戦略

- **iOS/Android**: 参考UI通りに完全統合（flutter_embed_unity）
- **Windows**: 立ち絵を Flutter で直接表示、Unity は将来 TTS/3Dモデル必要時に別ウィンドウで活用

この戦略により：
- 全プラットフォームで動く
- 卒研期間内で完成可能
- 本番リリースの主軸は iOS/Android
